# REFACTORING RULES & MANIFESTO

Статус: ACTIVE  
Дата принятия: 2026-09-16  

Данный документ регламентирует процесс рефакторинга кодовой базы Job Hunter CRM. Любые изменения в коде должны строго следовать этим правилам.

---

## 1. Мораторий на новые фичи (Feature Freeze)
- Во время рефакторинга действует строгий запрет на добавление новой бизнес-логики, кнопок, моделей ИИ, парсеров или изменение пользовательских сценариев.
- Задача рефакторинга — привести архитектуру к чистому, модульному, стабильному и легко читаемому виду без изменения внешнего поведения системы.

## 2. Сначала тест/слепок, потом изменение (Safety Net First)
- Ни один модуль или функция не переписывается без предварительного теста или фиксированного слепка поведения (Characterization Test).
- После любого изменения запуск тестов обязателен: `python3 -m unittest discover -s tests -p "test_*.py"`.
- Результат тестов должен быть 100% `PASS`.

## 3. Декомпозиция монолитов без усложнения стека (Zero New Frameworks)
- Строго соблюдаем ADR-001, ADR-002, ADR-003: Никаких React, Vue, Webpack, Vite, Django и т.д.
- Стек остается минималистичным: Python standard library + чистый Vanilla JavaScript.
- Функции размером > 200 строк подлежат декомпозиции на компактные, сфокусированные подфункции (Single Responsibility Principle).
- Каждая подфункция должна иметь четкие входные и выходные параметры без скрытых мутаций глобального состояния.

## 4. Четкие контракты данных (API & DTO Contracts)
- Все структуры данных (вакансии, отклики, профили кандидатов) должны иметь явные схемы полей.
- Никаких неявных `null`, отсутствующих ключей или угадываний формата в интерфейсе.
- Логика трансформации и валидации данных выполняется на бэкенде, фронтенд только отображает.

## 5. Абсолютная сохранность данных (Data Safety)
- База данных `jobs.db` и JSON-профили кандидатов неприкосновенны.
- Перед началом любого структурного вмешательства в схему или таблицы базы данных автоматически создается резервная копия (`jobs.db.backup_<date>`).
- Миграции схемы должны быть строго идемпотентными (безопасными при повторном запуске).

## 6. Атомарность шагов: «Один шаг — одна проверка»
- Запрещено менять бэкенд и фронтенд одновременно в одной итерации.
- Выбирается ровно одна длинная функция / один логический блок.
- Проводится декомпозиция → прогоняются тесты → проверяется запуск сервера через `./start.sh` → проверяется UI в браузере.
- Только после верификации переходим к следующей функции.

## 7. Принцип Анти-Халтуры (No Fake / No Mocks)
- Не прятать ошибки за пустыми блоками `try/except: pass`.
- Никаких заглушек, фейковых таймеров или имитации работы.
- Код пишется начисто, с понятными именами переменных и прозрачным потоком управления.
